## 0. 一句话定位

**一个自研、带原创形象的桌面伴侣桌宠：既是陪伴角色，也是 AI 工作状态的可见载体——能感知本机正在运行的 AI 编码 agent 工具，并据此做出差异化的形象 / 行为变化。首发（v1）只深度接入 Claude Code，其它 agent 工具留接口。**

> 🎯 **项目目标（用户 2026-10-09 补充，重要）**：**非商业项目**。目标是完成一个**完整的、可持续维护的项目**以丰富项目经历，**开源**。
> **（自媒体 / 传播工作已明确不在本项目开发范围内**——2026-10-09 用户决定。）
> **评估基准**：不按「市场可行性」评判，按「**作品集价值 / 可持续性**」评判。

> 🏷️ **项目命名（2026-10-09 定）**：中文展示名「**代码娘**」｜英文名 / 仓库名 / 包名：`code-musume`（标题展示可写 CodeMusume）。

## 1. 四轴决策结果（用户 2026-10-09 定）

| 轴 | 结论 | 说明 |
|---|---|---|
| **产品本质** | **双核心** | 陪伴感（性格、闲时行为、互动）与工作提示（agent 状态反应）同等重要，两条线都要做深 |
| **能力边界（v1）** | **仅状态反应** | 即：动作 / 气泡 / 声音。但架构上必须为「信息展示 → 权限审批 → AI 对话」保留可扩展空间（野心分阶段，不在 v1 实现） |
| **形象** | ⭐ **原创角色**（自己设计） | 不使用天选姬素材——版权上更干净，也让形象成为产品自身资产。**这解决了决策记录开放问题 #2** |
| **差异化机制** | ⭐ **agent 感知 + 差异化形象变化** | 探测本机正在运行的 agent 工具，据此做出「一定的差异化形象变化」——同一个角色，在不同 agent 工具下呈现不同面貌 / 姿态 |
| **形态** | 暂未定 | 单一角色产品 vs 可换角色的平台；架构上留余地 |
| **受众 / 发布意图** | 未明确 | 待定；不影响「是否存在类似产品」的调研本身，只影响结论怎么用（自用对标 vs 生态竞争） |

## 2. 范围与架构约束（用户原话要点）

> 「还要支持连接各个 agent 的 hook，不过初版只考虑完善 claudecode 相关功能，只为其他 agent 工具流出接口。」

推论（待方案设计阶段确认）：

- 需要一层**多 agent 适配层**：统一的「agent 状态事件」抽象，Claude Code 是第一个实现
- v1 验收范围 = Claude Code 的功能完整度；其它 agent 工具仅定义接口、不实现
- 沿用不变红线：hook 永远 `exit 0`、`async`、静默失败（见决策记录 §5）

## 3. 「类似产品」的判定基准（给调研用）

按本定义，一个产品与我们的相似度由以下维度叠加衡量：

1. **形态**：桌面伴侣 / 桌宠（角色常驻桌面）
2. **形象**：原创或自带角色（「泛用换皮容器」作为反向参考）
3. **感知**：感知本机 AI agent 工具的存在与状态
4. **差异化**：形象 / 行为随「哪个 agent 工具在运行」而变化 ⭐ **最独特的一条**
5. **集成深度**：对 Claude Code（或其它 agent）的 hook / 状态集成

> 2026-09 调研已知的部分交集：clawd-on-desk、clawd-conduit、agentpet、openpets、oc-claw 等（均为「Claude Code 桌宠」方向，但形象为现成 / 可换主题，感知面单一）。本次调研需核实其现状，并重点找：**多 agent 支持者、原创形象者、形象差异化机制者**。
>
> ✅ **2026-10-09 晚：本调研已完成**——结论见 `调研结论-2026-10-09-是否存在类似产品.md`。
> 要点：本表五个维度中，除「同一角色多形态」外均已有占位者（多 agent 已是及格线、原创形象已无壁垒）。
> **本定义文档的条文暂未改动，等待用户重新评估定位。**
