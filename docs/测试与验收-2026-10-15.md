# 固定数据、界面自动化与实机验收

日期：2026-10-15。现行产品与状态规则继续采用 2026-10-14 的四份设计规范。本文记录新增的测试体系，不能替代真实来源和人工验收。

## 怎么执行

|入口|检查内容|依赖|
|---|---|---|
|`pnpm test:replay`|按场景文件逐步比较 Rust 核心输出|Rust；无需桌面、账号或网络|
|`pnpm test:tools`|采集脱敏、关联保留和转发失败记录|Node.js|
|`pnpm test:ui`|启动实际 Tauri 程序，操作桌宠与设置、截图、冷启动与角色损坏恢复|Windows、WebView2、Rust、Node.js；首次安装独立测试依赖|
|`pnpm verify:desktop`|现有检查、事件通路、生产依赖隔离及界面验收|以上条件；视觉基准须已审阅|

界面工具依赖位于独立的 `tests/desktop` 工作区，避免为安装测试工具而调整产品依赖版本。手动安装：`pnpm --dir tests/desktop install --frozen-lockfile`。其构建白名单只允许 esbuild；embedded 驱动不需要下载 EdgeDriver 或 GeckoDriver。

调试测试脚本可执行 `pnpm test:ui -- --skip-build`，仅在对应测试构建已经是当前代码时使用。正常验收须重新构建。运行结果保存在忽略目录 `.test-artifacts/ui-*`，不会随源代码自动提交。

明确修改界面后，可用 `pnpm test:ui -- --review-candidates` 收集完整候选截图。此模式不比较或覆盖已有基准，整体仍以「待审阅」返回失败；功能与冷启动记录单独保留。逐图审阅后使用基准工具登记，再以普通模式重新验收。

## 固定场景与正确答案

场景位于 `fixtures/scenarios`，格式版本独立于业务协议。每份文件包含 `schemaVersion`、`id`、说明、来源版本、样本出处和顺序检查点。每步使用 `atMs` 注入单调时间，操作类型为 event、tick、lost、configure 或 reset。

每步必须明确预期 state、certainty、dominantAgent、pendingCount 和 formId；可以补充会话、提示、丢失数和诊断结果。对象比较允许只指定有关字段；数组要求数量和顺序一致。未知操作、字段、倒退时间或混用两家轮次字段会报错。失败输出场景、步骤、字段的预期值和实际值，并生成 `replay/result.json`。

正确答案根据状态规范审阅，禁止从当前 Engine 输出自动更新。来源分为：

- `synthetic`：用于边界与异常的合成数据。
- `real-redacted`：真实会话经过保留判断结构的脱敏处理。
- `derived-from-capture`：旧采集缺少关键字段，使用占位内容重建；不能称为原始真实载荷。

当前包含 21 个场景、110 个检查点，其中有 2026-10-15 Claude 真实只读会话的完整脱敏输入。旧的 2026-10-14 Claude 样本继续作为历史证据。

## 界面测试与截图

使用 WebdriverIO + Tauri embedded WebDriver，实际链路为 CLI → 本地 HTTP → Rust 核心 → Channel → 窗口。测试使用单独应用标识、配置、运行目录和 WebView profile。生产构建不包含 WDIO 插件、权限、时钟推进或窗口重建命令。

自动检查四个设置页面、Pixi/DOM 八种状态、来源与形态、待处理数量、保存和刷新、图片角色导入、错误反馈、隐藏恢复及窗口重建。系统托盘、原生文件选择框、物理焦点与穿透效果留给人工检查。自动选择下拉框通过真实页面 input/change 事件完成；不伪造 Rust 返回值。

长时限的界面检查只在测试构建中推进宿主时钟，仍经过同一串行核心。精确的期限边界由无实际等待的 Rust 场景覆盖。

截图仅针对项目窗口，通过 WebView2 CapturePreview 取得；测试固定 DPR=1、内容尺寸，减少动画并禁用 CSS 过渡。它不证明本机 125% DPI、拔屏或实际鼠标穿透通过。基准图必须经人工审阅，或由用户明确委托代理审阅，再连同真实审阅身份入库。缺少基准会输出候选图并使验收失败，不能当作截图比较通过。

像素比较 threshold=0.1，允许差异面积不超过 0.5%；文字、状态、待处理数、控件与配置仍采用严格断言。字体、WebView 和系统环境变更需要单独核对，不自动接受新图。

2026-10-15 用户提出“帮我完成决策”，委托 Codex 审阅初始画面。已检查 18 张桌宠图与 4 张设置页图，保留团子作为测试素材，正式美术后置。22 张基准及 `review.json` 已入库，记录 `user-delegated-agent` 和授权原话；不记作人工操作通过。后续更新基准仍需单独审阅，不从失败结果自动覆盖。

渲染回执包含实例 ID、修订号和宿主测得的毫秒数。只接受已经发布且属于当前实例的新修订。指标是收到事件到软件提交相应帧并回传的间隔，目标 ≤1 秒；不等同显示器扫描输出的时间。业务 v2 信封及 Projection 字段不变。

## 真实来源验收

1. 构建当前普通桌面程序及 CLI。
2. 执行 `node tools/live-session.mjs prepare --dir .test-artifacts/live-20261015`，在无敏感内容的项目内生成两家独立 hooks。
3. 执行 `node tools/live-session.mjs serve --dir .test-artifacts/live-20261015`，启动限定时长的观察器。
4. 在 Codex 桌面打开该隔离项目，确认编排及执行都在本机，按实际提供的入口审阅并信任项目和 hook 定义。不能编辑信任库或使用绕过信任的参数。
5. 提交“读取 fixture.txt，报告编号，不修改文件”。Claude 的同类只读会话可通过 `node tools/live-session.mjs claude --dir .test-artifacts/live-20261015` 执行，只向配置的服务发送公开测试文本。
6. 分别及共同触发正常工作、等待、中断和形态切换，然后执行同目录的 `report` 子命令生成来源报告。

观察器采用动态回环端口、独立令牌、启动探测、有界队列与超时。原始输入只在内存转发。持久化的会话、轮次、主体、工具和输入文本使用同轮采集内稳定的匿名值；错误标志与退出码保留。未知文本字段不进入日志。不访问 transcript。

`received` 只证明观察器收到；`forwarded.accepted` 证明宿主 HTTP 接受；`observed` 记录读取到的状态和渲染回执。必须核对回执修订号，旧回执不证明当前事件已显示。失败必须保留，不以收到事件代替验收。

当前已核实 Claude Code 2.1.295 与 Codex 桌面内置运行时 0.162.0-alpha.17.2。运行时版本不等于 Codex 桌面 UI 的独立版本。Codex 实机、真实双来源与人工项目尚待实际证据，不由自动脚本的合成事件替代。
