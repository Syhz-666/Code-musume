## 日志确认的失败

| 检查 | 首个失败 | 后续现象 |
| --- | --- | --- |
| windows | `tools/smoke.ps1` 的 `Claude working` | 第一条 hook 静默退出，但状态未达到 working；旧报告未保留当时快照，无法从原日志确认丢失或延迟的具体阶段 |

## 已确认的测试缺陷

1. 冒烟脚本启动 hook 后才调用 `ConvertTo-Json` 准备输入。hook 的 300ms 总预算已开始运行，慢机器或首次序列化可能在输入送达前耗尽预算。现在先完成序列化，再启动进程；等待状态时在有限时间内检查已接收事件的处理结果，不重发事件，不延长真实 hook 截止。
2. 界面场景缺少统一的开始状态恢复。`pixi-waiting` 截图失败会跳过工具完成事件，留下等待；后续场景又共享预览、形态和渲染方式。现在每个测试先恢复配置、清理工作状态并刷新两个测试窗口。形态保存测试自行建立 Codex 工作状态；最后一个场景显式保存 DOM 设置供独立重启检查验证。
3. 过去截图比较依赖本机字体。固定的只有 DPR 和窗口尺寸；基准记录为 WebView 156，CI 日志为 155。字体、字体回退、栅格化环境差异是截图失败的候选原因，尚无 CI 实际图与差异图确认具体像素来源。现在 e2e 构建使用仓库内固定的 OFL 字体子集，等待字体就绪，固定颜色配置并记录环境。正常构建不包含字体或测试插件。
4. 截图差异在记录后继续执行剩余流程，最后统一失败。差异面积上限仍为 0.5%，像素比较阈值仍为 0.1，没有自动接受新基准。失败时补存诊断、预览快照与最终前端字段；CI 上传这些 JSON、日志及截图。

## 第二轮：补充日志与本地复现（2026-10-30 收尾）

用户更新的日志对应首轮修补后的运行。以下是新证据，不替代上面的历史记录。

| 项目 | 日志／实验结果 | 处理与结论 |
| --- | --- | --- |
| smoke | `Claude working; state=idle; pending=0; missed=1` | 已在本机 Windows PowerShell 中稳定复现：当控制台输入编码为带 BOM 的 UTF-8，.NET 创建子进程 stdin 的 StreamWriter 时会写入 `EF BB BF`。随后直接写 BaseStream 也不能消除已有 BOM。JSON 被核心判为无效输入，因此状态没有变化。 |
| 动画 | idle／thinking／working 停在第 0 帧，`animationRunning=false` | 程序会尊重系统的减少动画偏好；旧 CI 日志缺少该字段，尚不能认定它就是云端原因。测试现在显式固定无减少动画，另起一轮真实启用系统减少动画，分别验证两种情况。生产偏好判断不变。 |
| 截图 | 仅角色与偏好两个可滚动设置页不同 | 滚动条／内容宽度是候选原因，未获得 CI 实际图与差异图前不作最终归因。e2e 固定 12px 滚动条，记录内容宽度和差异区域；仍严格使用 0.1 像素阈值和 0.5% 面积上限。 |

smoke 修补在 `Process.Start` 前临时设置无 BOM 的 UTF-8 输入编码，启动后立即恢复原编码；不放宽生产 JSON 校验，不延长 hook 截止。CI 新增带 BOM 控制台环境的回归步骤。

### 新增诊断证据

- CLI 记录输入字节数、BOM／UTF-8／JSON 检查、各阶段耗时与 HTTP 结果；短事件摘要可与宿主记录关联。
- 宿主记录鉴权／Origin／限流／输入拒绝、核心前后状态、快照发布与画面回执。报告不保存原始输入或认证信息。
- 界面失败独立保存核心和两个窗口现场，包括系统与应用动画偏好、手动预览、修订号、字体、DPR、内容／滚动条宽度与 WebView 版本。截图失败不会阻止 JSON 保存。
- 测试日志中的 `D:\a\Code-musume\Code-musume` 和 `C:\hostedtoolcache\windows\node\…\node.exe` 是云端 runner 自己的工作目录与 Node 安装位置，不是把开发机路径写入测试配置。
